# 📱 個人手機記帳 App (MVP) 系統功能與架構規格書

## 1. 專案概述與目標 (Project Overview)
本專案旨在開發一款專供**個人使用**的手機記帳 App，支援 **iOS** 與 **Android** 雙平台。產品定位為 **MVP（最小可行性產品）**，核心價值在於提供極簡、流暢的單手輸入體驗，以及即時的每月消費統計圖表。

* **開發框架建議：** Flutter (Cross-platform)
* **資料儲存架構：** 方案 A — 純手機本地端儲存 (Local Storage)，無後端伺服器與 API，保障用戶隱私與單機高回應速度。

## 3. 系統功能需求 (Functional Requirements)

### 3.1 記帳輸入模組 (Transaction Input Module)
* **系統自動初始化：** 每次開啟記帳畫面，系統須自動擷取手機當前之系統日期作為預設消費日期。
* **消費類別選擇：** 提供快捷分類按鈕，內建預設類別（如：早餐、午餐、晚餐、交通、娛樂等）。
* **自訂計算機鍵盤：** 畫面配置自訂數字鍵盤，包含 `0-9` 數字鍵、`Delete`（退格鍵）與 `Enter`（確認儲存鍵）。

### 3.2 歷史與圖表模組 (Dashboard & Analytics Module)
* **即時刷新機制：** 用戶按下 `Enter` 儲存後，主畫面之歷史消費清單須在無須手動重整或換頁的情況下，原地即時更新。
* **每月統計圖表：** 系統須依據當前月份，自動加總各分類之消費總額，並以圖表（如圓餅圖或條形圖）呈現各類別支出比例。

## 4. 系統流程與控制邏輯 (System Flows & Logic)

### 4.1 記帳儲存與畫面刷新流程
當用戶於自訂鍵盤點擊 `Enter` 鍵時，系統須依循以下邏輯時序執行：

1. **資料檢核 (Validation)：**
   * 檢查輸入金額是否大於 0。
   * 檢查是否已選取消費類別。
   * *異常流 (Alternative Flow)：* 若任一檢核失敗，中斷後續流程，並於畫面上跳出提示訊息（e.g., "請輸入金額與類別"），保留用戶已輸入的內容。
2. **本地寫入 (Local Database Write)：** 檢核通過後，異步（Asynchronous）將「金額、類別 ID、消費日期」寫入手機本地資料庫。
3. **狀態廣播與重繪 (State Notification & Re-render)：**
   * 資料庫寫入成功後，狀態中心（State Provider）發出變動通知。
   * 「歷史清單組件」與「統計圖表組件」收到通知，自動重新向本地資料庫讀取最新數據並即時重繪 UI。
4. **輸入區重設 (Input Reset)：**
   * 清空金額（重設為 0）。
   * *體驗優化 (UX Optimization)：* **保留**最後選取的類別與消費日期，以利使用者進行連續同類別或同日期的記帳作業。

## 5. 本地資料庫設計 (Database Schema Specification)

本系統採用單機關聯式資料庫結構，設計兩張核心資料表：`categories`（類別表）與 `transactions`（記帳明細表），兩者具有 **一對多 (One-to-Many)** 的關聯關係。

### 5.1 資料表：`categories` (記帳類別表)
* **用途：** 儲存消費分類定義。

| 欄位名稱 (Column) | 資料型態 (Type) | 條件約束 (Constraint) | 欄位說明 (Description) |
| :--- | :--- | :--- | :--- |
| `category_id` | `INTEGER` | **PK**, Auto Increment | 類別唯一識別碼 |
| `category_name` | `TEXT` | NOT NULL | 分類名稱（如：早餐、午餐） |
| `icon_name` | `TEXT` | NULL | 前端對應顯示的圖示編號/名稱 |
| `display_order` | `INTEGER` | DEFAULT 0 | 畫面顯示的排序權重（數字越小排越前） |

### 5.2 資料表：`transactions` (記帳明細表)
* **用途：** 記錄每筆實際消費明細。

| 欄位名稱 (Column) | 資料型態 (Type) | 條件約束 (Constraint) | 欄位說明 (Description) |
| :--- | :--- | :--- | :--- |
| `transaction_id` | `INTEGER` | **PK**, Auto Increment | 帳目唯一識別碼 |
| `amount` | `INTEGER` | NOT NULL | 消費金額（限制為正整數） |
| `category_id` | `INTEGER` | **FK**, NOT NULL | 關聯至 `categories.category_id` |
| `transaction_date` | `TEXT` | NOT NULL | 消費日期，格式統一為：`YYYY-MM-DD` |
| `created_at` | `TEXT` | DEFAULT CURRENT_TIMESTAMP | 系統寫入時間戳記 |

## 6. 邊界條件與潛在風險防禦 (Edge Cases & Safety Defenses)

作為資深 SA，針對本 MVP 系統提出以下防禦性設計要求：

* **金額溢位防禦 (Integer Overflow)：**
  由於使用自訂鍵盤，為防範不小心連續按到零導致數值超出資料庫整型（Integer）上限，自訂鍵盤輸入上限強制設為 **7 位數（最大金額 9,999,999）**，超過則不接受輸入。
* **資料孤兒防禦 (Data Integrity)：**
  `transactions.category_id` 設為外鍵限制（Foreign Key Constraint），不允許寫入不存在的類別 ID。若未來開放刪除分類，須採用「級聯刪除 (Cascade Delete)」或「禁止刪除已被引用之分類」之商業邏輯。
* **單機資料遺失風險 (Data Loss Risk)：**
  由於採純本地儲存，手機遺失或解除安裝 App 將導致資料永久遺失。
  * *建議未來迭代方案：* 於第二階段（Phase 2）規劃「一鍵匯出 CSV」功能，允許用戶將資料備份至個人 Google Drive 或 iCloud。
